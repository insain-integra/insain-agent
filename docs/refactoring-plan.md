# План построения системы управления проектом

> Составлен: 2026-09-28, переработан: 2026-10-24. Живой документ: задачи отмечаются по мере
> закрытия критериев. После запуска `todo/` (фаза 5) крупные пункты отсюда переезжают в задачи.

## Задача

Построить для компании Инсайн систему, в которой один человек через ИИ-агентов в Cursor управляет
сайтом insain.ru, расчётным ядром и их развитием — по единому циклу
**задача → агент → проверка → ревью → деплой**.

Приоритет: сначала harness (порядок, правила, проверки, конвейер), потом продукты.

### Контуры

| Контур | Состав | Статус и правило |
|---|---|---|
| 1. Сайт insain.ru | WordPress на VDS, формы ezFC, страницы, WooCommerce, SEO, меню, медиа, bridge-плагин | главный продуктовый контур |
| 2. Расчётное ядро | `calc_service`: API калькуляторов, справочники цен | единый источник цен; цены меняются только в git |
| 3. ИИ-консультант | `bot_service`: Telegram-бот, база знаний | **консервация**: тесты зелёные, не развивается, на VDS не разворачивается |
| 4. Harness | `AGENTS.md`, `todo/`, роли, `make check`, CI, skills | средство, не продукт |

### Два типа контента сайта

| Тип | Что | Источник правды | Как меняет агент |
|---|---|---|---|
| Кодоподобный | custom JS форм ezFC, привязка форм к slug API, цены и справочники | репозиторий | правка в git → проверка → деплой / импорт в WP |
| Редакционный | страницы, тексты услуг, товары Woo, SEO, меню, медиа | WordPress | по задаче из `todo/` через wp-cli / REST / Browser MCP; в репозитории — инвентарь, правила, журнал |

Репозиторий управляет тем, что ломается без контроля версий, и описывает остальное.
Полный экспорт WordPress в git не делаем.

### Люди

- Единственный оператор — владелец проекта: ставит задачи, делает финальное ревью, подтверждает
  опасные действия на проде. Контент и цены помимо него никто не меняет.
- Второй оператор возможен позже: правила, роли и задачи живут в репозитории, ничего не завязано
  на локальные пути и личные учётки.

### Не входит

Редизайн сайта; замена WordPress / ezFC / WooCommerce; переписывание бота; многопользовательская
оркестрация агентов; внешние трекеры; полный экспорт WP в репозиторий; развитие бота и Max до снятия паузы.

### Критерии успеха

1. Любое изменение в любом контуре проходит один цикл, и агент по `AGENTS.md` выполняет его без устных пояснений.
2. Цены на сайте и в API совпадают и меняются в одном месте; расхождение невозможно по процессу, а не по дисциплине.
3. Состояние прода (сайт, формы, API, версии) описано в репозитории, совпадает с реальностью и проверяется командой.
4. Новая форма, калькулятор, правка страницы или товара делаются по рецепту (skill) с проверкой результата на сайте.
5. Бот не деградирует: его тесты входят в `make check`.

## Принципы порядка работ

- Свести расхождения раньше, чем документировать.
- Почистить раньше, чем описывать.
- Поставить проверки и CI раньше, чем расширять автономию агента на проде.
- Конвейер (роли, задачи) включать только после того, как есть `make check` и чистый прод.
- Ретроспектива точечно: агент ошибся → одна строка в `AGENTS.md` или одна проверка в `make check`.

## Исполнители

По умолчанию — быстрая модель (Grok 4.7). Сильная (Opus 5.5) — только там, где ошибка дорогая
или текст станет конституцией проекта. Человек вычитывает правила для агентов до коммита.

| Задача | Исполнитель | Почему |
|---|---|---|
| 0.1, 0.3, 1.x, 2.x, 3.2–3.6, 4.x, 5.3–5.5, 6.x | Grok 4.7 | узкий scope, проверяемые критерии |

## Протокол выполнения

Для агента, который берёт задачу из этого плана. Не читать план целиком.

1. Одна задача = одна сессия с чистым контекстом. Читать только этот протокол, блок своей задачи
   и файлы из строки «Контекст». Весь план, `CLAUDE.md`, `docs/archive/vds-wordpress-docker-setup.md`,
   `docs/project_summary.md`, `bot_service/agent.py` целиком — не открывать; только grep по месту.
   `ROADMAP.md` удалён, идеи — в `BACKLOG.md` (текст файла — в истории git).
2. Критерий «Готово» — это команда. Выполнить её и привести вывод, не писать «проверено».
3. Не выходить за scope. Соседняя проблема — одна строка в отчёте, не правка.
4. После закрытия: отметить чекбокс и дописать «сделано ДД.ММ.ГГГГ, проверено: \<команда\>».
5. Отчёт: сделано / чем проверено / не сделано и почему / требуется решение. Без пересказа плана.
6. Остановиться и спросить: изменение прода вне списка «делай сам» в
   `.cursor/rules/insain-site-autonomous.mdc`; удаление; `git push` в `main`; выбор между
   конфликтующими ценами, если правило по умолчанию не сработало.

### Грабли окружения

- PowerShell: `&&` не работает, разделитель `;`.
- Git на VDS: `git -c safe.directory=/opt/insain-agent -C /opt/insain-agent …`.
- wp-cli: `sudo -u www-data wp … --path=/var/www/insain.ru`.
- Полный pytest обеих сюит ~4 минуты; для петли сначала `calc_service/tests`.
- SSH с первого раза может отвалиться по таймауту — повторить, не менять подход.
- Прод-порт API `8002` (nginx → `127.0.0.1:8002`), не `8001`. Старые доки врут.

### Решения по умолчанию

- **0.2.** Цены с прода верные, если локальная правка не младше по `git log`. Одна и та же позиция
  изменена по-разному в обоих местах и даты не решают — стоп, таблица различий, спросить.
- **0.3.** Истина — `docker inspect insain-calc-api` (порты, volumes, команда), не любой compose-файл.
  Репозиторий подгоняется под работающий контейнер.
- **0.4.** Прод переключается на `main` после локального слияния. `git push` в `main` — спросить.
- **0.5.** Короткий простой API на время пересборки допустим. Перед пересборкой:
  `docker tag` текущего образа как `insain-agent-calc-api:rollback`. Откат:
  поднять контейнер с тегом `rollback`, проверить `curl -sS -o NUL -w "%{http_code}" https://insain.ru/api/v1/calculators`.
  Делать в спокойное время, не в рабочий пик сайта.

## Фаза 5. Конвейер агентов

Оценка: 1 день на подготовку, далее — обкатка на реальных задачах. Основа — task-driven подход:
задача как спецификация в репозитории, роли как фокус, детерминированная проверка до сдачи.

- [ ] **5.1. `todo/` — задачи как спецификации.** `todo/AGENTS.md` (полстраницы правил), шаблон
      задачи (цель; контекст и ссылки; scope / не-scope; критерии приёмки; проверки; риски — прод,
      цены, формы; результат — ветка, PR или коммит), шаблон эпика для того, что не влезает в один PR.
      После закрытия файл удаляется; устойчивое знание — в `docs/`.
      *Готово:* первая реальная задача проведена через шаблон от постановки до merge.

- [ ] **5.2. Четыре роли** в `docs/agents/roles/`, по 20–40 строк:
      **Analyst** — пишет и уточняет задачу, прод-код не трогает;
      **Implementer** — код, тесты, доки по задаче; сдаёт только после `make check`;
      **Reviewer** — diff против критериев задачи, регресс, инварианты; не переписывает «красивее»;
      **Site ops** — операции на проде и в WordPress по правилу `insain-site-autonomous`.
      *Готово:* на роль можно сослаться одной фразой («Reviewer, проверь todo/…»), и агент меняет фокус.

- [ ] **5.3. Три режима работы** — закреплены в `AGENTS.md`:
      **быстрый** (один файл, цена, опечатка) — правка + `make check`, просмотр diff;
      **обычный** (калькулятор, bridge, форма, модуль) — `todo/` → Implementer → self-review →
      Reviewer → финальное ревью человека → merge; новая сессия на этап при распухшем контексте;
      **прод** (VDS, WP, данные на сервере) — Site ops, подтверждение человека на опасных шагах.

- [ ] **5.4. Git-правило:** обычный и прод режимы — ветка от `main`, PR или коммит с описанием задачи;
      быстрый — по усмотрению. Прод деплоится только с `main`.

- [ ] **5.5. Skills для повторяемых рецептов** в `.cursor/skills/`: деплой плагина; новый калькулятор;
      изменение цены в JSON с выкаткой; перевод формы ezFC на API. Роль говорит *кто смотрит*,
      skill — *как делать руками*.
      *Готово:* каждый skill прогнан хотя бы раз на реальной задаче.
