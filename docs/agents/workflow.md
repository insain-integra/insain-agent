# Маршруты между ролями

Роли: [Analyst](roles/analyst.md), [Implementer](roles/implementer.md), [Reviewer](roles/reviewer.md),
[Site ops](roles/site-ops.md) и человек. Модель — не роль: она в шапке задачи.

Задачу между ролями передаёт человек. Агент заканчивает сессию итогом из таблицы «Итоги»,
пишет его в «Журнал передач» задачи и ставит статус. Следующую роль он сам не запускает.

## Статусы

Строка `Статус:` в шапке — одно из значений ниже; проверяет `calc_service/tests/test_todo_files.py`.

| Статус | Значит | Ставит |
| --- | --- | --- |
| `черновик` | задача написана, работа не начата | Analyst |
| `в работе` | идёт сессия Implementer или Site ops | Implementer, Site ops |
| `ревью` | сдано, ждёт Reviewer или слияния | Implementer, Site ops |
| `доработка` | Reviewer вернул блокеры | Reviewer |
| `выкатка` | ветка слита в `main`, ждёт Site ops | человек |
| `закрытие` | выкачено и проверено на проде, ждёт закрытия человеком | Site ops, Reviewer |
| `заблокировано: <роль>` | ждёт роль: `аналитик`, `исполнитель`, `ревьюер`, `site ops`, `человек` | любая роль |
| `заблокировано: ждёт todo/<имя>.md` | ждёт закрытия другой задачи; файла `todo/<имя>.md` нет — `make check` красный | Analyst; снимает `python scripts/dev.py close <имя>` |
| `готово` | закрыто человеком | человек |

## Цепочки

Режим и наличие прод-шагов задаёт Analyst в задаче (поле `Site ops` в шапке).

- **Обычная** (код, тесты, доки): Analyst → Implementer → Reviewer → человек (слияние) → закрыто.
- **Смешанная** (git, затем прод: формы ezFC, цены в JSON, плагин): Analyst → Implementer → Reviewer →
  человек (слияние, `выкатка`) → Site ops → человек (закрытие). Задача на копию формы ezFC:
  Implementer (git) → Site ops (дубль, JS и GET на копии, прогон) → человек (приёмка копии) → Reviewer →
  человек (`finish-task`); расхождение на копии — обратно Implementer. Боевая форма — только после слияния.
- **Прод без git** (меню, страница, SEO, товар): Analyst → Site ops → человек. Reviewer — только если
  поле `Reviewer` в шапке заполнено, а не `не нужен`; смотрит отчёт Site ops с выводами команд, а не diff.
  В смешанной задаче Reviewer смотрит только diff, отчёт Site ops — нет.

После выкатки и проверки — статус `закрытие`: человек принимает результат на сайте и закрывает задачу.

## Итоги

| Роль | Итог | Статус | Дальше |
| --- | --- | --- | --- |
| Analyst | задача написана, «Файлы» ни с кем не пересекаются | `черновик` | Implementer или Site ops по цепочке |
| Analyst | задача написана, «Файлы» пересекаются с `todo/<имя>.md` | `заблокировано: ждёт todo/<имя>.md` | человек: после закрытия той задачи ставит `черновик` |
| Analyst | задача поправлена по блокеру | статус до блокировки | роль, которая заблокировала |
| Implementer | сдал, `make check` зелёный | `ревью` | Reviewer |
| Implementer | критерий невыполним, противоречив, нет данных | `заблокировано: аналитик` | Analyst |
| Implementer | нужно решение по цене или бизнесу | `заблокировано: человек` | человек |
| Implementer | две неудачные попытки, сессия на Grok | `заблокировано: исполнитель` | новая сессия Implementer на Opus 5.5 |
| Implementer | две неудачные попытки, сессия на Opus | `заблокировано: человек` | человек |
| Implementer | нужен факт или действие на проде | `заблокировано: site ops` | Site ops |
| Reviewer | `принято` по diff | `ревью` | человек: слияние |
| Reviewer | `принято` по отчёту Site ops | `закрытие` | человек: закрытие |
| Reviewer | есть `блокер` | `доработка` | Implementer |
| Reviewer | `не могу принять` | `заблокировано: <роль>` | критерий не проверить локально — по правилу «Site ops или человек»; критерий двусмыслен — Analyst; diff не разобрать — Implementer (разбить на коммиты) |
| Site ops | выкачено, smoke зелёный | `закрытие`; прод без git с `Reviewer` не `не нужен` — `ревью` | человек: закрытие; или Reviewer |
| Site ops | smoke упал, откат сделан | `заблокировано: исполнитель` или `человек` | по правилу «Site ops или человек» |
| Site ops | проверка по запросу сделана | статус до блокировки | роль, которая заблокировала |

Отчёт любой роли заканчивается готовым промптом следующей сессии в блоке `text`: роль, модель из шапки,
`todo/<имя>.md`, ветка, что проверить. Дальше человек — вместо промпта одна фраза, что ему сделать.
Принятую задачу человек завершает skill `finish-task` (коммит, слияние, `close`, пуш).

## Site ops или человек

- Критерий не проверить локально: Site ops — если его закрывает команда или действие по
  `insain-site-autonomous.mdc` без отдельного подтверждения (`curl`, wp-cli на чтение, страница под админом).
  Человек — если нужно суждение (вид страницы, приёмка копии, цена «как надо»), опасный шаг из «Запретов»
  `AGENTS.md` или доступ, которого у агента нет. В блокере — команда или вопрос, которые надо выполнить.
- Откат после упавшего smoke: откат не вернул прод в прежнее состояние — всегда `человек`, даже если
  причина видна в git. Прод вернулся: `исполнитель` — причина в git (код, JSON, `forms/<slug>.js`), её видно
  в логе или ответе API; `человек` — причина вне git (сервер, WordPress, кэш, доступ) или не ясна.

## Блокер

Лимит — две попытки на одно и то же, третьей нет. Перед остановкой — запись в «Журнал передач»:

```
Блокер: <что не получается>
Пробовал: <попытки и вывод команд>
Гипотеза: <почему>
Вопрос: <что решить>
Следующая сессия: <роль>, модель <…>
```

## Ревью и доработка

- Замечания — в файл задачи, раздел «Ревью N» (N — круг), каждое с меткой `блокер`, `желательно` или `вне scope`.
- `вне scope` не держит сдачу и уходит в «Найдено вне scope».
- Implementer правит блокеры; `желательно` — только отмеченные человеком.
- Повторное ревью — та же модель Reviewer, только diff после прошлого круга и закрытие блокеров.
- Тот же блокер в третьем круге — `заблокировано: аналитик` (критерий понят по-разному)
  или `заблокировано: исполнитель` с моделью Opus 5.5.
- Несогласие Implementer с замечанием — строка в «Журнал передач»; решает человек.

## Находки вне scope

- Implementer, Reviewer и Site ops файлы в `todo/` не создают и `BACKLOG.md` не правят.
- Находка мешает задаче — это блокер для Analyst: он расширяет scope или заводит задачу-предпосылку,
  а текущей ставит `заблокировано: ждёт todo/<имя>.md`. Оба файла — в `main`, не в ветке задачи:
  `close` снимает «ждёт» только там. Расхождение порта с JS — skill `port-fix-prerequisite`.
- Не мешает — строка в «Найдено вне scope»: что, где, почему важно. Работа продолжается.
- При закрытии человек разбирает раздел: строка в `BACKLOG.md`, задача через Analyst или отказ.

## Новая задача от человека

- В чат работающего агента не дописывать.
- Сырая идея — строка в `BACKLOG.md` в `main` (быстрый режим).
- Делать сейчас — новый чат Analyst. Он сверяет строку «Файлы» со всеми задачами в `todo/`, кроме `готово`:
  пересечения нет — параллельно; есть — новой задаче `Статус: заблокировано: ждёт todo/<имя>.md`,
  а в эпике ещё и «после todo/<имя>.md» в «Порядке».
- Прод сломан — быстрый режим в отдельном worktree от `main`; активные ветки после этого — rebase на `main`.

## Параллельные задачи

- Одна задача — одна ветка — один worktree — одно окно Cursor. В папке, где работает агент, ветки не переключать.
  `git worktree add ..\insain-agent-<имя> -b task/<имя> main`
- Параллельно идут только задачи, у которых строки «Файлы» не пересекаются.
- Общие файлы: `STATUS.md`, `BACKLOG.md`, `docs/site/forms.md`, `docs/history/log.md`, `docs/dashboard.md`,
  `calc_service/calculators/__init__.py`, `calc_service/data/common.json`, версия в `wp-plugin/insain-calc-bridge.php`.
  В параллельной группе их правит одна задача; другие пишут нужную правку в «Результат», её вносят при слиянии.
- Слияние — по одной ветке: rebase на свежий `main` → `make check` → `git merge --ff-only`. Следующая — после этого.
- Прод — последовательно: одна сессия Site ops за раз, деплой API и выкладка плагина не параллелятся.
- После слияния и закрытия — `git worktree remove ..\insain-agent-<имя>` и `git branch -d task/<имя>`.
