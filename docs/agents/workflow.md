# Маршруты между ролями

Роли: [Analyst](roles/analyst.md), [Implementer](roles/implementer.md), [Reviewer](roles/reviewer.md),
[Site ops](roles/site-ops.md), [Orchestrator](roles/orchestrator.md) и человек. Модель — не роль: она в шапке задачи.

Задачу между ролями передаёт человек или [Orchestrator](roles/orchestrator.md) (субагентами до первой остановки на человеке).
Все остановки, подтверждения и развилки для человека оформляются через `AskQuestion` с готовыми вариантами (`.cursor/rules/interactive-choices.mdc`).

## Статусы

Строка `Статус:` в шапке — одно из значений ниже; проверяет `calc_service/tests/test_todo_files.py`.

| Статус | Значит | Ставит |
| --- | --- | --- |
| `черновик` | задача написана, работа не начата | Analyst |
| `в работе` | идёт сессия Implementer или Site ops | Implementer, Site ops |
| `ревью` | сдано, ждёт Reviewer или слияния | Implementer, Site ops |
| `доработка` | Reviewer вернул блокеры | Reviewer |
| `выкатка` | ветка слита в `main`, ждёт Site ops | человек |
| `закрытие` | выкачено и проверено на проде, ждёт закрытия человеком | Site ops, Reviewer |
| `заблокировано: <роль>` | ждёт роль: `аналитик`, `исполнитель`, `ревьюер`, `site ops`, `человек` | любая роль |
| `заблокировано: ждёт todo/<имя>.md` | ждёт закрытия другой задачи; файла `todo/<имя>.md` нет — `make check` красный | Analyst; снимает `python scripts/dev.py close <имя>` |
| `готово` | закрыто человеком | человек |

## Три трека (цепочки)

Трек задаёт Analyst (или человек при постановке задачи):

1. **Быстрый** (1–3 файла в одном контуре: цена в JSON, мелкий баг-фикс, правка копии формы, доки/правила):
   без файла в `todo/`, без отдельной ветки и без `Reviewer`. Один агент делает правку и `make check`, затем через `AskQuestion` предлагает коммит / push / выкатку.
2. **Поточный** (типовая задача по готовому skill: копия формы ezFC, однотипный калькулятор, `Сложность: низкая`):
   ветка `task/<имя>` в основной папке. При `Reviewer: не нужен` цепочка:
   Analyst → Implementer (+ Site ops по копии без отдельного «да» на черновик) → человек (приёмка через `AskQuestion`) → `finish-task`.
3. **Полный** (боевые формы, массовые правки БД/WordPress, конфликт цен, новый модуль):
   - Обычная: Analyst → Implementer → Reviewer → человек (`finish-task`).
   - Смешанная: Analyst → Implementer → Reviewer → человек (слияние, `выкатка`) → Site ops → человек (`finish-task`).
   - Прод без git: Analyst → Site ops → (Reviewer, если `Reviewer` ≠ `не нужен`) → человек (`finish-task`).

После выкатки и проверки — статус `закрытие`: человек принимает результат через `AskQuestion` и закрывает задачу.

## Итоги

| Роль | Итог | Статус | Дальше |
| --- | --- | --- | --- |
| Analyst | задача написана | `черновик` (или `заблокировано: ждёт todo/<имя>.md`) | Implementer или Site ops по цепочке |
| Analyst | задача поправлена по блокеру | статус до блокировки | роль, которая заблокировала |
| Implementer | сдал, `make check` зелёный, `Reviewer` ≠ `не нужен` | `ревью` | Reviewer |
| Implementer | сдал, `make check` зелёный, `Reviewer: не нужен` | `ревью` (или `закрытие`, если прод не нужен) | человек (`finish-task`) или Site ops (если прод-копия) |
| Implementer | критерий невыполним, нет данных | `заблокировано: аналитик` | Analyst |
| Implementer | нужно решение по цене/бизнесу или развилка | `заблокировано: человек` | человек (через `AskQuestion`) |
| Implementer | две неудачные попытки, сессия на Grok | `заблокировано: исполнитель` | новая сессия Implementer на Opus 5.5 |
| Implementer | две неудачные попытки, сессия на Opus | `заблокировано: человек` | человек (через `AskQuestion`) |
| Implementer | нужен факт или действие на проде | `заблокировано: site ops` | Site ops |
| Reviewer | `принято` по diff | `ревью` | человек: слияние (`finish-task`) |
| Reviewer | `принято` по отчёту Site ops | `закрытие` | человек: закрытие (`finish-task`) |
| Reviewer | есть `блокер` | `доработка` | Implementer |
| Reviewer | `не могу принять` | `заблокировано: <роль>` | Site ops, человек, Analyst или Implementer по причине |
| Site ops | выкачено / копия отлажена, smoke зелёный | `закрытие` (или `ревью`, если нужен `Reviewer`) | человек (`finish-task`) или Reviewer |
| Site ops | smoke упал, откат сделан | `заблокировано: исполнитель` или `человек` | по правилу «Site ops или человек» |
| Site ops | проверка по запросу сделана | статус до блокировки | роль, которая заблокировала |
| Site ops | сессия на Grok: шага нет в skill или две попытки | `заблокировано: site ops` | новая сессия Site ops на Opus 5.5 |

Отчёт роли заканчивается либо готовым промптом следующей сессии в блоке `text`, либо (если дальше человек) карточкой `AskQuestion` с готовыми вариантами действий. Принятую задачу завершает skill `finish-task` одним действием без повторного переспроса про `git push`.

## Site ops или человек

- Критерий не проверить локально: Site ops — если его закрывает команда или действие по `insain-site-autonomous.mdc` без отдельного подтверждения (`curl`, wp-cli, дубль формы на черновике товара). Человек — если нужно визуальное суждение, переключение живой боевой формы, опасный шаг из «Запретов» `AGENTS.md` или смена цен/бизнес-логики.
- Откат после упавшего smoke: не вернул прод в прежнее состояние — `человек`; прод вернулся и причина в git — `исполнитель`; причина вне git — `человек`.

## Блокер

Лимит — две попытки на одно и то же, третьей нет. Перед остановкой — запись в «Журнал передач»:

```text
Блокер: <что не получается>
Пробовал: <попытки и вывод команд>
Гипотеза: <почему>
Вопрос: <что решить>
Следующая сессия: <роль>, модель <…>
```

## Ревью и доработка

- Замечания — в файл задачи, раздел «Ревью N», с меткой `блокер`, `желательно` или `вне scope`.
- `вне scope` не держит сдачу и уходит в «Найдено вне scope».
- Implementer правит блокеры; `желательно` — только отмеченные человеком.
- Повторное ревью — та же модель Reviewer, только diff после прошлого круга.
- Тот же блокер в третьем круге — `заблокировано: аналитик` или `заблокировано: исполнитель` (Opus 5.5).

## Находки вне scope

- Implementer, Reviewer и Site ops файлы в `todo/` не создают и `BACKLOG.md` не правят.
- Расхождение порта с JS на **не-боевом** калькуляторе (не используется ни на одной боевой форме на API) — чинится в текущей задаче с эталоном из раннера и проверкой тестов соседей, без создания отдельной предпосылки (`ezfc-form-to-api` / `port-fix-prerequisite`).
- Расхождение на **боевом** калькуляторе API (меняет цены/сроки живых форм) — оформляется предпосылкой `todo/<fix>.md`.
- Не мешает задаче — строка в «Найдено вне scope».

## Ветки и папки

- **Никаких дополнительных папок и `git worktree` за пределами корня репозитория.**
- Вся работа идёт в основной папке `insain-agent`:
  - быстрый трек — сразу в `main`;
  - поточный и полный треки — в ветке `task/<имя>` от `main`.
- В основной папке не запускаются одновременно два агента с правками на разных ветках. При необходимости переключиться на другую задачу незакоммиченные правки текущей ветки сначала коммитятся (WIP) или согласуются с человеком через `AskQuestion`.

## Слияние и закрытие

Сливает и закрывает агент по выбору человека в `AskQuestion` или по команде («принято, закрывай», «закрывай», «finish-task») — skill `finish-task`. Роли и `Orchestrator` не сливают и не закрывают без выбора человека.

| Цепочка | Момент | Команда / выбор человека | Что происходит |
| --- | --- | --- | --- |
| Обычная; поточная; копия формы ezFC | Reviewer `принято` или `Reviewer: не нужен` и сдача | «Принято, закрывай» | коммит в `task/<имя>` → fast-forward в `main` → `make check` → `close` → коммит закрытия → `push` → удаление ветки `task/<имя>` |
| Смешанная, слияние перед продом | Reviewer: `принято` | «Принято, слить и выкатить» | коммит в `task/<имя>` → fast-forward в `main` → `make check` → статус `выкатка` → `push`, CI → удаление ветки; дальше Site ops на `main` |
| Смешанная, закрытие; прод без git | Site ops: `закрытие` | «Закрывай» | `close` → коммит закрытия → `push` |

## Параллельные задачи

- В одной папке репозитория одновременно идёт одна git-ветка `task/<имя>`. Параллельно можно вести задачи без конфликта по ветке (прод-чтение, анализ, `Site ops` на `main`).
- После слияния ветки в `main` — `git branch -d task/<имя>` и `git push origin --delete task/<имя>`.
